# QueryGuard v1.3.0

QueryGuard is a PostgreSQL migration lock linter plus a synthetic query-plan smoke test. This release makes it safe to rely on as a CI gate: it now fails closed, its fixes are tested, and its documentation says only what it does.

`@v1` now points at this release, so **if you use the Action, read [Upgrading](#upgrading) first.** No existing Action input was removed or renamed.

## Highlights

### It fails closed
Every run now ends in one of three statuses, shown first in the PR comment and the job summary.

| Status | Meaning |
| :--- | :--- |
| **PASS** | Every check ran, and the rules found nothing. |
| **FAIL** | A migration statement failed to apply (the report gives the statement, line number and Postgres error), or a lock or transaction hazard was found. |
| **INCONCLUSIVE** | Something could not be checked, so this is **not** a pass. The report lists exactly what was skipped and why. |

- A failed baseline schema statement stops the run as INCONCLUSIVE. A failed migration statement stops it as FAIL.
- A table the synthetic generator can't populate, a query that fails under `EXPLAIN`, or a missing `schema-path`/`migration-path` file is skipped, listed, and makes the run INCONCLUSIVE.
- Nothing is ever reported as PASS if anything was skipped.
- **Exit codes** (strict mode, `fail-on-sev1: 'true'`): `0` PASS, `1` FAIL, `2` INCONCLUSIVE. In advisory mode (the default) the job always passes, and the report still leads with the status. Unrecoverable errors (Postgres unreachable, `queries-path` unreadable) exit `1` in both modes.
- The report is also written to the GitHub job summary.

### Sequential scans are informational
Query plans come from ~2,000 generated rows, so a sequential scan there is a hint, not evidence of a problem. Scans now appear under *Informational: sequential scan on synthetic data*. They **never** affect the status, the exit code or `fail-on-sev1`, and the report states that a clean query section is not evidence of production safety. Only migration findings can fail strict mode.

### Fixes you can trust
- Remediation is built from your parsed statement. `CREATE INDEX` becomes the same statement with `CONCURRENTLY` inserted, preserving `UNIQUE`, `USING`, `INCLUDE` and `WHERE`. This fixes the old suggestion that rendered `ON${table}` with no space and ended in `...`.
- `ALTER COLUMN … TYPE` now gets executable SQL for the staged approach (add a nullable column, backfill, swap), including your `USING` expression.
- Index suggestions for sequential scans are checked against the catalog and quote identifiers properly (a column named `user` no longer produces broken SQL). If a column can't be determined, no SQL is emitted.
- Every emitted fix is tested to pass QueryGuard's own lint and to execute on Postgres 16.

### Transaction awareness
`CREATE INDEX CONCURRENTLY` cannot run inside a transaction block.
- It is now flagged when it appears between `BEGIN`/`START TRANSACTION` and `COMMIT` in the same file.
- New input **`assume-in-transaction`** (CLI: `--assume-in-transaction`, default `false`) for runners that wrap every migration file in a transaction, as Rails and Django do by default. When set, `CONCURRENTLY` is flagged and the migration runs inside `BEGIN`/`COMMIT`, so you see the real Postgres error.
- Every index fix now says how to opt out: Rails `disable_ddl_transaction!`, Django `atomic = False`, or a separate migration outside a transaction.

### Better detection
The hand-rolled parsing was replaced with a tokenizer, which means:
- Quoted and schema-qualified table names are parsed correctly (unnamed indexes used to be reported against the wrong table), and `ALTER COLUMN … TYPE` inside multi-action `ALTER TABLE` statements is now caught.
- The word `CONCURRENTLY` inside a string literal (for example in a `WHERE` clause) no longer makes an index look safe.

## Upgrading

Most repos need no changes. These existing setups may see different results:

1. **Strict mode (`fail-on-sev1: 'true'`) can now exit `2`.** If the generator can't populate a table, or `schema-path`/`migration-path` points at a missing file (previously silently skipped), the run is INCONCLUSIVE and fails the job. Fix the cause (see the report's *Skipped* table), or use advisory mode.
2. **Repos that failed only on sequential scans now pass.** If you relied on that to block merges, it no longer does.
3. **New findings are possible** from the broader detection above, and from `CONCURRENTLY` inside a transaction.
4. **Rails and Django users:** set `assume-in-transaction: 'true'` so `CONCURRENTLY` is judged the way your runner will run it.
5. **Integers without defaults:** an `int` primary key or unique column with no default can't be populated (the generator reuses small values). That table is now reported as skipped, making the run INCONCLUSIVE, where before the failure was swallowed.
6. **PR comments** now carry a new hidden marker, and the report heading is "QueryGuard Report" (the column is "Impact"). Comments written by earlier versions are still found and updated in place, not duplicated.

`fail-on-sev1` keeps its name for compatibility; it now means "strict mode".

## Documentation
- The README now describes what the tool does: a migration lock linter plus a synthetic query-plan smoke test. It documents the three rules, statuses and exit codes, `assume-in-transaction`, and known limitations. "Blast-radius" claims and unmeasured latency figures are removed.
- The `AGENTS.md` template's `CONCURRENTLY` advice is now conditional on the migration not running inside a transaction.
- The web sandbox is rewritten to match, with no invented numbers, and is labelled as a simplified preview.
- Privacy wording is corrected: the only network calls are to the GitHub API to post the comment, and the comment contains your statements and table names.

## Known limitations
- **Three rules only:** `CREATE INDEX` without `CONCURRENTLY`, `ALTER COLUMN … TYPE`, and `CONCURRENTLY` inside a transaction. No findings does not mean a migration is safe. The type-change rule is conservative and also flags changes Postgres can do without a rewrite.
- **Synthetic data is simple:** it can't populate custom or enum types with `NOT NULL`, or generated columns, and only fills tables in the `public` schema.
- **Needs a privileged Postgres role:** row generation sets `session_replication_role`, which requires superuser.
- **Schema-only dumps:** the baseline is split into statements, so `COPY … FROM stdin` data blocks aren't supported.
- **Hand-written parsing:** unusual syntax can still be missed. Evaluating a real parser is written up in [docs/spikes/parser.md](https://github.com/queryguardhq/queryguard/blob/main/docs/spikes/parser.md); nothing from it is wired in.

## Under the hood
- `package.json` is the single version source; the CLI help reads it at build time (it previously said v1.2.0 while the package was 1.2.3).
- CI runs the test suite against a Postgres 16 service container, typechecks, and fails if rebuilding `dist/` changes it. The repo's own check no longer overwrites the bundled `dist/index.js` with unbundled output.
- Releases are tag-triggered: check the tag against `package.json`, build, test, publish with npm provenance, then move `v1`. This release carries an npm provenance attestation.
- Removed stray `dist/reporter.js` and `dist/types.js`.
